# Decisions after the ledger recording move — #1108

No behavior changes in this file have been implemented. #1109 waits for the owner. The current module has two operations: record a new Expense/payment, and change an existing Expense. A writer supplies the facts; the module performs the ordered save.

There are **20 entries from reply 53's settings inventory**, plus **two gaps in changes to an existing Expense** that have no setting. The entries below are grouped by what someone could notice. Field names are in brackets for an implementer. “Keep” means preserve a deliberate distinction and give it a clearer name where useful; “correct” is a recommendation for the owner to decide, not authorization to change it here.

The nine `recording-*.integration.test.ts` snapshot files under `apps/web/src/lib/__snapshots__/` record today's answers and stored effects. Supplemental baselines live in `batch-recording`, `settlement-recording`, `expense-recording`, `recurring-recording` and `expense-change-recording.integration.test.ts`. Named cases below are searchable there. Interleaving records pause a real database write and commit a state change; they do not themselves run a complete leave/removal journey. Where relevant, the cleared-balance examples explain how the same state can be reached through admitted requests.

## Who may record, and when archiving takes effect

### 1. A single payment can record after a person leaves [compatibility.membership: before-retry]

**Today and trigger.** A single payment checks the actor, payer and recipient before looking for a previous recording, but never checks them again at insertion. A same-currency payment does not require an existing Debt: with cleared balances, a named person or the actor can leave after admission and before insertion. A batch and a new manual Expense recheck at commit. A single-payment retry after a named person has already left is instead refused before its receipt is found.

**What differs / proof.** The racing single payment returns **201** and changes the ledger with a former member; a new manual Expense/batch refuses. An actor departure should be **403**, and a missing named person **422**. Records: single payment's `actor leaves between the checks and the commit`, `named person leaves between the checks and the commit`, and retries after departure. The ordinary retry difference also appears in entry 3.

**One behavior / effect / recommendation.** Admit the current actor, recognize an already completed command, and check current people again for a new financial effect. Stale single-payment requests would refuse instead of creating new Debt. **Correct — real access/financial gap.**

### 2. A batch checks people even before acknowledging an old receipt [compatibility.membership: before-retry-and-at-commit]

**Today and trigger.** A batch checks actor and named people both before retry lookup and at commit. Its archive refusal occurs later than some other writers' initial checks. If a person leaves after a successful batch, its unchanged retry can be refused even though that batch is already recorded. Manual Expenses can acknowledge such a retry.

**What differs / proof.** The client may see **422** rather than its successful recorded response. Batch records cover departure before retry and at commit; `batch-recording.integration.test.ts` pins archive/participant/currency precedence. No client should infer that this refusal undid the old payments.

**One behavior / effect / recommendation.** Use the common admission/receipt rule from entry 1, keeping checks on a _new_ batch at commit. Lost-response retries would acknowledge an existing batch after participant departure. **Correct the replay distinction; keep commit checks.** This does **not** re-open the earlier all-or-nothing decision for a batch.

### 3. An Expense acknowledges an old save without requiring its old participants to remain [compatibility.membership: actor-before-retry]

**Today and trigger.** Manual Expenses and member-saved assistant Drafts check the actor before normalization/replay. For a first save they validate participants, and check them again at commit. A retry can still succeed after one of the Expense's old participants left, or the Group was archived, provided the actor still has access.

**What differs / proof.** The client gets its original **201** record rather than a new participant/archive refusal. This does not create another Expense. Records: retries after a named person leaves or the Group is archived; first saves in those states still refuse. The supplemental archived-Group/missing-participant case also pins **409 before 422** for a new Expense.

**One behavior / effect / recommendation.** Make this the common rule for acknowledging completed commands. Payments' lost-response handling becomes less surprising; current actors still cannot make a new write using departed participants. **Keep the distinction between replay and new save, with a name such as “admit actor, then recognize receipt.”**

### 4. A generated Expense keeps its template's creator as actor, but skips all commit-time people checks [compatibility.membership: template-validated; checkPeople omitted]

**Today and trigger.** Recurring generation validates its template against an initial Group read. It later inserts without rechecking creator or participants. The creator may have left while the template still names other current people; it may also lose a named participant between validation and insertion.

**What differs / proof.** A read can generate an Expense attributed to the former creator. Its alert excludes that creator and includes only involved current members. That attribution/exclusion is **deliberate, #841; do not re-decide it**. A departed payer/participant can also remain in the newly generated financial effect, which is a separate gap. Recurring records cover creator departure, named-person departure, the commit interleavings and the audience.

**One behavior / effect / recommendation.** Keep the historical creator as attribution, while validating current financial participants at insertion. A failed generation remains a read-safe skip/retry, not a new error from the read. **Keep creator attribution with a better name; correct the coupled participant-check gap.** “Template creator as actor” and “template people checked at commit” should be independent rules.

### 5. A vanished Group is a server fault for a single payment [compatibility.missingGroup: fault]

**Today and trigger.** The route admits an actor, then the Group disappears before the single-payment service reads it. That service throws a plain “Group not found” fault. Other new-record writers answer lack of access. This can occur when a previously admitted request resumes after final-member cleanup.

**What differs / proof.** The client gets **500 `{ error: 'Internal server error', status: 500 }`**, rather than **403 `FORBIDDEN`**. Record: `the Group vanishes after route admission and before the service reads it` in the single-payment recording.

**One behavior / effect / recommendation.** Treat disappearance as lost access at this seam, without revealing Group existence. Web/Android/payment API clients would get a definite refusal rather than uncertainty about server health. **Correct — real refusal gap.**

### 6. On standalone Mongo, a late archive can still admit a payment or Expense [compatibility.standaloneArchive: fence-only]

**Today and trigger.** A single payment or manual/reviewed Expense passes the standalone fence's archive check; an independent archive commits while currency locking is under way. The subsequent Group read deliberately does not refuse that archive. Replica-set inserts do not have this exception. Batches already require transactions.

**What differs / proof.** A client can receive **201** and find a new record in an archived Group. The payment and Expense supplemental tests each perform an independent archive after the standalone currency check and assert that result.

**One behavior / effect / recommendation.** Enforce the archive seen by the final Group read before insertion on both topologies. The demonstrated request would get **409 `GROUP_ARCHIVED`**. **Correct the explicit exception.** Standalone support itself is a separate deployment decision; a reread does not give standalone Mongo the full atomic guarantees of a replica set.

### 7. Recurring generation can write after an archive on a replica set too [compatibility.archive: before-generation]

**Today and trigger.** The generator sees an open Household, then it is archived before the Expense's recording fence. That fence is not marked as a ledger write and the module does not recheck archive. Other new-record paths do.

**What differs / proof.** The Expense-list read still answers **200**, but now includes a new Expense in an archived Group, with Activity and an advanced marker. Record: recurring `archive commits after the checks and before the recording fence`.

**One behavior / effect / recommendation.** The insertion must obey the same archive rule as other financial records. Because generation is read-safe, the corrected read still answers normally, adds no Expense and leaves that failed period for its normal retry policy. Members would stop seeing post-archive additions. **Correct — real financial gap.**

### 8. A financial edit can retain a participant who left after the initial Group read [change operation; no setting]

**Today and trigger.** An edit checks participants only for a financial change, using the Group snapshot read before its first fence. Clear Sam's old balance, start an edit increasing the amount while still naming Sam, then let Sam leave before the edit commits. The new money can still be saved. A new Expense validates current people at commit.

**What differs / proof.** The editor gets **200**, and the ledger can acquire new Debt involving a former member; the alert correctly excludes that former member. Record: edit `named person leaves between the checks and the commit`, which pauses at the first fence. The before/after audience-union cases also remain relevant.

**One behavior / effect / recommendation.** Recheck changed financial participants at commit. A racing financial edit would refuse **422**, while a notes/Tag-only edit of historical money can remain allowed. **Correct the financial-edit gap; keep nonfinancial edits of history possible.** Do not turn this into a blanket ban on editing any old Expense naming a former member.

### 9. A delete can finish after its actor leaves [change operation; no setting]

**Today and trigger.** Delete checks access at admission only. After everyone settles the old Expense, its actor can leave with zero balance while an already admitted delete is waiting; the Expense is then deleted anyway. The change operation also has no general commit-time actor check for edit/restore.

**What differs / proof.** The stale actor receives **200** and the ledger changes after access was lost. Record: delete `actor leaves between the checks and the commit`. The audience is current-member-filtered; that does not reauthorize the financial change.

**One behavior / effect / recommendation.** Verify the current actor at the financial commit for changes as for new member-started records. The stale delete/edit/restore should refuse **403**. **Correct — real access gap.** Historical `deletedBy`/Activity attribution remains for changes that were authorized when committed.

## What a retry means

### 10. A member save has a submission key; a generated Month has a schedule identity [retry.key versus retry.template/period]

**Today and trigger.** Manual Expenses and single payments accept a client submission key; older/trusted key-less calls create a new recording each time. A batch requires its key. Reviewed Draft saving has its own outer receipt. Generation uses the template and Month, so a changed template does not rewrite an already recorded Month.

**What differs / proof.** Same key and same command returns the old record; changed command conflicts. Two key-less saves are two records. A repeated Month is one Expense even if the template changed. Records: same/changed-command, key-less saves, `a changed template keeps the recorded Month`, and three-Month catch-up.

**One behavior / effect / recommendation.** All writers need a stable identity for one intended financial effect, but those identities cannot honestly all be a client header. **Keep as deliberate, with explicit submission/Month names.** Requiring keys from remaining legacy callers would be a separate client compatibility change, not removal of recurring identity.

### 11. A stale generated-Month retry locks currency before recovering an existing record [retry.lookup: on-duplicate]

**Today and trigger.** Generation tries insertion and looks up its Month only after a duplicate. Other writers first look for a receipt. With a stale generation marker and an existing pending event, a failed currency lock prevents recovery and marker advancement even though the financial record already exists.

**What differs / proof.** The read remains **200** with one Expense, but Activity can remain pending and the marker stays behind; an upfront replay could recover it. The supplemental `locks currency before recovering an already recorded month with a stale marker` demonstrates this using committed legacy currency drift. Modern template creation already locks the main currency, so that drift is not a normal public currency-change journey; **nobody outside the server can tell in the ordinary successful retry, but a test can**. Storage failure/legacy state makes the recovery timing observable.

**One behavior / effect / recommendation.** Recognize an existing Month before performing new-write currency work, while retaining the generator's early recorded-marker skip. That would improve recovery for the exceptional state, without creating a second Expense. **Correct the unnecessary duplicate-only lookup distinction.** The feed remains a recovery path either way.

### 12. A batch receipt names the complete ordered group of payments [retry.receipt: ordered-records]

**Today and trigger.** A batch can create multiple currency rows. Its receipt stores all their IDs in order; a retry loads exactly that set. A single payment or Expense has one record. Missing IDs/rows are faults, rather than success with part of a batch.

**What differs / proof.** The client always gets the same ordered complete batch, or a fault if stored data is corrupt. Records: multi-currency batch/replay; baseline `keeps a corrupt batch receipt a fault` covers missing ordered IDs and a missing stored row.

**One behavior / effect / recommendation.** One logical command must acknowledge its whole effect. **Keep — deliberate all-or-nothing batch behavior.** A name such as “ordered batch receipt” makes the reason clearer. Flattening this to “find one record” would lose payments and is not a valid unification.

### 13. A batch looks for a competing receipt again inside its fence [retry.atCommit]

**Today and trigger.** Two same-key requests start before either sees a receipt. A batch's second check can return the winner before later row validation or preparation. Other writers normally attempt insertion and recover a matching duplicate.

**What differs / proof.** An already recorded batch can be returned despite a currency/presentation state changing while the second request waits. The batch inner-replay baseline pins the winner's response before those later refusals. In a normal same-state race the clients see the same successful receipt either way; only the timing/state transition reveals the difference.

**One behavior / effect / recommendation.** A common commit-time receipt check could make acknowledgments consistent, but it would alter other writers' refusal precedence. **Keep for now with a name such as “confirm competing batch before row checks.”** The owner should decide the precedence explicitly before deleting or generalizing it; batch atomicity itself is already decided.

### 14. An old Tag name can conflict in a race but replay successfully a moment later [retry.raceCommand: original]

**Today and trigger.** An Expense save loses a duplicate-key race after its submitted old Tag name has been reused. The race compares the command normalized before waiting; an ordinary retry normalizes through the stored receipt's immutable Tag identity. Both paths describe the same already recorded submission.

**What differs / proof.** The existing baseline is **201 / 409 / 201** for winner, racing attempt and ordinary retry. Record: `a reused old Tag name conflicts in the duplicate race but replays ordinarily`, for manual Expense/Draft saving.

**One behavior / effect / recommendation.** Confirm the stored submission identity consistently in both retry paths. The racing client would receive its recorded Expense immediately, instead of an avoidable conflict followed by success. **Correct.** This changes a client-visible answer and belongs only in #1109.

### 15. An Expense remembers the legacy Tag name originally submitted [retry.legacyTagAlias]

**Today and trigger.** A legacy client sends `Food`; the Tag later becomes `Meals`, or the Expense is reassigned. The receipt keeps the original alias and stable identity so the unchanged old request can still be recognized. Modern clients can send a Tag ID. Payments have no Tag.

**What differs / proof.** The old client gets its original Expense rather than a spurious Tag/conflict refusal. Records cover ordinary old-name retry, rename/reuse and explicit new Tag identity. The financial-identity tests retain explicit-ID precedence.

**One behavior / effect / recommendation.** All paths should recognize an immutable submission identity; supporting old-name clients requires this saved fact. **Keep as deliberate compatibility data, named “submitted Tag alias.”** Deleting it would break old-client lost-response recovery; it is not merely a timing option.

### 16. Successful retry responses disagree about a renamed Tag's display label [prepareResponseRecord outcome/group]

**Today and trigger.** An ordinary Expense replay resolves its display label through the admission Group, but a duplicate-race response keeps the stored label. Both are successful and refer to the same stable Tag. Expense and batch descriptions also populate their people; a single payment populates after returning from the module.

**What differs / proof.** A client reading the returned `tag` label may see `Food` after the race and `Meals` on the next retry. Record: `the duplicate-race response keeps the stored Tag name, then an ordinary retry rewrites it`. Persisted identity is unchanged. Publication-before-response-failure checks pin that population failure does not suppress Activity.

**One behavior / effect / recommendation.** Resolve current display labels consistently for successful responses, while keeping publication before fallible presentation. **Correct the retry-kind label difference; keep response preparation as a writer responsibility.** The module could stop passing retry kind to this hook once no description needs it; the hook itself still earns its place for population.

## Atomicity, currencies and values read while a request waits

### 17. A batch requires transactions; ordinary writes still support standalone Mongo [transactions]

**Today and trigger.** A batch must create all its payment rows or none, so standalone Mongo answers **503 `SETTLEMENT_TRANSACTIONS_REQUIRED`** before recording. Single payments, manual Expenses and generation retain standalone support. Saving reviewed Drafts separately requires a transaction around the Expense and Draft acknowledgment.

**What differs / proof.** Batch clients on a standalone deployment cannot record that command; they do not get a partially recorded set. Real standalone batch/payment/Expense records and Draft transaction suites prove the distinction.

**One behavior / effect / recommendation.** Requiring transactions for every writer would remove standalone ordinary-write support. Allowing standalone batches would abandon atomicity. **Keep — the batch's required transactions and all-or-nothing behavior are deliberate earlier decisions.** Name the requirement after atomic multi-record recording; do not ask the owner to re-approve partial batches.

### 18. New money needs a listed currency; an existing Debt can outlive the list [currencies rule and per-row currencies]

**Today and trigger.** A new Expense or a payment's paying currency must be listed. A payment may settle Debt in a historical currency still held by the ledger. Restoration can use an unlisted currency if another live Expense/payment still holds it; the deleted Expense itself does not count. Each batch row declares its own settled/paying currencies.

**What differs / proof.** Removing a listed currency does not make old Debt unpayable, but does block new money in an unlisted currency. Restore can instead say to add that currency first. Records: removed paying currency, historical settled currency and moved/restored Expense; currency-route tests cover another live Expense, a Settlement, and self-only deleted history.

**One behavior / effect / recommendation.** One rule for _all currency uses_ would either strand old Debt or admit arbitrary new currencies. **Keep the deliberate distinction**, preferably with names “new money” and “existing Debt,” plus a restore-specific rule. These are business conditions, not inconsistent implementations to erase.

### 19. A failed generated insertion can leave its currency lock committed [currenciesAt: before-fence]

**Today and trigger.** Generation commits its currency lock separately, then inserts the Expense. Other creation writers lock inside their insertion transaction. If insertion fails, generation can leave `currencyLocked: true` with no new Expense. The record uses a stored template whose Group starts unlocked; modern template creation already locks it, so ordinary new templates generally conceal the difference.

**What differs / proof.** The recorded legacy-state Group's settings remain locked after the failed read; the comparable manual insert rolls its lock back. Record: `a failed first insertion leaves the currency lock the writer committed`. For a normally created, already locked template, **nobody outside the server can tell, but a test can**; the extra independent transaction still exists.

**One behavior / effect / recommendation.** Lock generation's currency in the same transaction as its new record, while leaving template creation's own rule alone. The failed generation would not newly lock the legacy empty Group. **Correct the unnecessary separate commit**, together with the event-timing consequences in entry 21. Standalone transactions remain limited as described in entry 17.

### 20. A batch reads presentation data after waiting; a single payment can keep earlier names [prepareAt: commit]

**Today and trigger.** A single payment reads payer/recipient names before waiting for its recording fence. A batch reads names after its commit-time receipt check. Rename Sam while the write waits: the Activity metadata may carry the old name for a single payment and the new name for a batch. Other preparation also captures IDs, metadata and event timing.

**What differs / proof.** Members/clients reading Activity metadata can see different name snapshots. `batch-recording.integration.test.ts` has `reads batch names after waiting for the fence`; the payment timing/name baseline pins the other order. This is observable even though financial amounts agree.

**One behavior / effect / recommendation.** Read display names at one chosen point for recorded events, independently of financial normalization. **Leave this setting until the owner chooses that point**, then rename it after what is actually read. Moving every kind of preparation together would also change timing and refusal precedence; “make all preparation late” is not a harmless cleanup.

## Activity and alerts

### 21. Activity time may describe preparation rather than insertion [activity.occurredAt]

**Today and trigger.** Manual/reviewed Expense descriptions supply the time captured before their fence. Recurring supplies the time after its separate currency lock but before insertion. Payment events are built later; change events/history/deletion timestamps are captured before their second save fence. Delay a fence by 500 ms and the saved record's timestamp can be later than Activity.

**What differs / proof.** API clients can compare the timestamps, and feed ordering can reflect the earlier event time. Supplemental manual, recurring and edit/delete/restore timing cases pin the exact values. This is not a different amount or duplicated record.

**One behavior / effect / recommendation.** Choose whether Activity means command/preparation time or financial commit time, then apply that meaning consistently. **Leave pending that product/audit choice.** Removing `occurredAt` would silently choose commit-side event construction time and change existing feed data. The owner should decide it alongside entries 19–20, not as an incidental refactor.

### 22. Manual Expense-added alerts are unconditional; other families have their own rollout switches [activity.alert.switch]

**Today and trigger.** Manual and member-reviewed Draft additions always capture their eligible audience, irrespective of the Expense-change switch. Generated additions and edit/delete/restore use the Expense-change switch; payments use the independent Payment switch. Captured recipients are current involved members, without the actor; edits take the before/after union.

**What differs / proof.** With one switch off and the other on, the stored alert context—and later eligible Android push—differs by event family. All four switch combinations are recorded for each writer, alongside actor exclusion and audience-union cases. **Unconditional manual/reviewed Expense-added capture is deliberate #840. The template creator as actor/excluded recipient is deliberate #841.** Do not re-decide either under a “single switch” cleanup.

**One behavior / effect / recommendation.** One switch for all events would change rollout and notification behavior for members. **Keep deliberate policies with names after the event families**: ordinary Expense addition, Expense change/generated addition, and payment. Actual delivery also has its own global controls; capturing context does not itself mean a push was sent.

## Description facts and one additional finding

`groupId`, `actorId`, the Expense/payment model, the normalized `command`, participant validation, each row's ID/document/event metadata, involved people, `prepare`/`build` and response population describe the writer's facts. They are not hidden policy toggles. The creation result's `created` boolean only lets generation count a new Month. The change operation's absent expected revision remains for trusted in-process seed callers; HTTP supplies the parsed displayed revision. A null change result is the already-deleted early return; no Activity means an edit still saves/publishes pending work without inventing a new event. Neither skips the module's admission/revision checks. No new setting was introduced for entries 8–9.

**Reported source-check finding:** Tag rename still backfills stable Tag IDs on legacy Expenses (`tag-management.service.ts`, `submit`, `Expense.collection.updateMany(legacy, { $set: { tagId } }, { session })`). It emits no financial edit, revision or Activity because it binds the _same_ Tag's old name to its identity. The check lists this exact call explicitly as **inline identity migration**, not an ordinary writer exception. No behavior was changed and no extra module operation was quietly added. Recommendation: **keep this identity-preservation maintenance, with its explicit narrow exception**; a future decision to centralize identity maintenance would be a separate operation from recording money.

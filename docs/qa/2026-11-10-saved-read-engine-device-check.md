## Finding #1043: native HTTP cache answers after clock rollback

W23 isolated this on Tags. W24 establishes the broader scope and replaces the unmerged Tags-only proposal with one Android request policy. The earlier observations follow unchanged; W24's tables and final result are below.

The unchanged-clock control used the same installed R8 dev APK and original Metro source. As Alex, open Manage Tags, close it and reopen it from Maple House three times. All three reopens reached the backend: `/tag-actions` GET 200 at 01:02:45.156, 01:02:54.452 and 01:03:03.715 UTC. Screenshots: `w23/control-reopen-{1,2,3}.png`.

With automatic time off and the device one day back, the unmodified warm reopen, pull to refresh and whole-Group reopen all showed the earlier Tags without a backend Tags request. Screenshots: `w23/rollback-reopen.png`, `w23/rollback-pull.png`, `w23/rollback-group-reopen.png`.

Temporary tracing ruled out a stopped manager. `open` mounted a new manager; `run` saw `mounted: true`, `current: true`, `busy: false`; recovery settled; refresh, `client.read`, the query function, the engine's `read` / `fetchOne`, `tagRequest` and transport `fetch` all ran. No `Superseded` interrupted the read. At `client.read`, stale time was `-Infinity`, fetch status was idle, and a new fetch started. The watcher could show the cached Tags while fetching, but it did not stop the fetch. The detailed safe trace is `w23/trace.log`; selected lines and proxy evidence are in `w23/investigation.log`.

The stop is below JS, in the native HTTP cache. The baseline transport response at device time `1794273201035` had `Date: Tue, 10 Nov 2026 01:13:21 GMT`. After rollback, transport returned 200 at device times `1794186818339` and `1794186818483` with that exact old Date, no Cache-Control, Expires, ETag or Last-Modified, and no corresponding proxy/backend request. Adding only request `Cache-Control: no-cache`, while keeping the clock back, produced a backend GET at 01:14:31.858 UTC and a new response Date of 01:14:31. Thus the successful fetch was a native cached response, not a fresh server verification.

Installed Expo 58's `ExpoFetchModule.kt` creates its client through React Native's `OkHttpClientProvider.createClient(reactContext)`. That provider configures a 10 MB `http-cache`. The Tags route's `success(...)` response supplies no cache policy. Connected assistants' auth endpoints explicitly send `Cache-Control: no-store`, consistent with their passing result. The same transport and Tags response behavior exists on main `0063a64e`, verified by source inspection rather than a second device build. Main additionally uses zero Tags stale time, so it also has the query-level rollback issue addressed by #1031. The warm-open control rules out a generic screen-reopen failure.

## W24: source check and Android change

The repo uses React Native 0.88.0 and Expo 58. Gradle's `app:dependencyInsight --configuration debugRuntimeClasspath --dependency com.squareup.okhttp3:okhttp` resolves **OkHttp 4.9.2** (`okhttp-dependency.log`). React Native's `OkHttpClientProvider.createClient(context)` supplies a 10 MB `cache/http-cache`; Expo's `ExpoFetchModule` uses that provider, and `NativeRequest.start` passes request headers to OkHttp without a cache override.

In [OkHttp 4.9.2's cache strategy](https://github.com/square/okhttp/blob/parent-4.9.2/okhttp/src/main/kotlin/okhttp3/internal/cache/CacheStrategy.kt#L141), request `no-store` makes `isCacheable` false before freshness is considered, so an existing entry is not used. The [cache interceptor](https://github.com/square/okhttp/blob/parent-4.9.2/okhttp/src/main/kotlin/okhttp3/internal/cache/CacheInterceptor.kt#L122) checks the same predicate before storing the network response. A request header therefore covers both reuse and storage; no fetch cache option or native client setting is needed. The strategy's age calculation subtracts the stored receive time from the current wall clock, explaining why rollback can otherwise make an answer appear fresh.

Branch `codex/1043-transport-no-store`, based on `74b094d0`:

1. `8a92eccf`: red-first transport read/write matrix, notification fetch assertion, and the W23 controller regression adapted to start with an HTTP response left by an older build. Before the fix, 10 cases failed and 92 passed. Existing assertions were not loosened.
2. `a408fb79`: add `Cache-Control: no-store` in the transport header builder for every request and to the separate notification-task fetch; add the README sentence. No path patterns, cache deletion, server change or ADR amendment.

The retained controller case adds an observable guarantee beyond header presence: newly read Tags reach the snapshot after rollback despite an old native response. With the fix, the focused files pass all 102 tests (transport 70, Tags saved copies 30, runtime notifications 2). Full mobile 4,226 and shared 2,075 tests pass; typecheck, lint (five existing web warnings), root format and unchanged ceilings pass. All **19 gate steps pass in 274.5 seconds** on an isolated Mongo replica set at 27143. Standards and Spec reviews found no findings.

### Existing-cache deletion: owner decision, not implemented

Headers stop serving and adding entries but do not remove old bytes. One option is a one-time native upgrade cleanup before any HTTP client opens that directory. Another is a native hook on the active Expo/OkHttp cache calling `Cache.evictAll()` after relevant in-flight requests are quiesced, integrated with sign-out/account change. The latter needs coordination with Expo's client, which is separate from React Native's singleton; clearing only that singleton is insufficient. A live directory must not simply be removed under open clients. Either option adds native lifecycle/bridge code and tests, does disk work proportional to the cache (10 MB cap here), and evicts other HTTP assets sharing it. A sign-out hook also adds a purge completion/failure policy to decide. No such policy or cache deletion was added, and ADR 0006 was not amended.

From OkHttp 4.9.2's [cache age calculation](https://github.com/square/okhttp/blob/parent-4.9.2/okhttp/src/main/kotlin/okhttp3/internal/cache/CacheStrategy.kt#L239), these entries remain eligible until the phone's clock catches up to each entry's original response/storage time, or the cache evicts it. For the one-day rollback here, that is approximately the displaced day, not a new server-side TTL. This duration is inferred from the source and stored timestamps; no 24-hour wait was performed. Restoring the correct clock makes the entry stale and allows a fresh request, but the observed private/no-store response did not overwrite or delete the old entry. Another rollback before its original timestamp therefore made it eligible again.

The server policy prevents new API HTTP-cache entries and protects a pre-fix app with fresh cache data. It cannot change headers on an old response that prevents any request reaching it. W24's Android request policy addresses that separate path; the accepted app branch was not exercised again in W25. No mitigation or deletion code was added in this device-only round.

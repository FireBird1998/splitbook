# The MCP server is a route in the web app, authorized by Better Auth

Members want to ask an AI assistant about their ledger ("who still owes me for Goa?", "what did August cost us?") and, later, to record an Expense or Settlement through it. We expose Splitbook as a remote Model Context Protocol server at `/api/mcp` inside `apps/web`, the same Next.js deployment that already serves the web app and the Android client, instead of adding a separate backend service. Better Auth becomes the OAuth 2.1 authorization server for MCP clients through its official `@better-auth/mcp` plugin, so an assistant acts as exactly one signed-in member, subject to the same invite-only allowlist, membership checks, money rules and idempotency as the HTTP API. Both entry points call one actor-scoped ledger operations module, so an MCP tool cannot drift from the route that shows the same data.

## Considered options

- **A separate MCP service (`apps/mcp`) that calls the HTTP API.** Rejected: it adds a deployment, a second auth surface (it would need to hold user sessions or mint its own tokens) and network hops, and it would only proxy logic the web app already owns. Revisit if the MCP workload needs a different runtime or scaling profile from the web app.
- **A separate backend service for all clients (web, Android, MCP).** Rejected: the web app's route handlers, Mongoose services and Better Auth already are that backend, and ADRs 0003 and 0004 build on it. None of the triggers for a split exist today: no long-running or scheduled jobs (recurring Expenses materialize on read), no persistent connections, no heavy server compute, no second runtime. The gap that did exist, authorization and read behavior living in route handlers, is closed by the shared operations module rather than a new service.
- **A local stdio MCP server with a personal API token.** Rejected as the product path: it works only for one technical user on one machine, needs a hand-rolled token system with its own revocation, and cannot serve hosted assistants. It remains acceptable as a throwaway development harness.
- **Hand-rolled OAuth on top of Better Auth sessions.** Rejected: the MCP authorization profile (protected resource metadata, audience-bound tokens, client ID metadata documents, PKCE) is exactly what the maintained plugin implements; owning it would repeat the mistake ADR 0003 moved away from.

## Consequences

- Better Auth moves from 1.7.3 to at least 1.7.7 (the plugin's peer range) and gains the `jwt`, `mcp` and `cimd` plugins plus their collections. MCP access tokens are JWTs verified against the app's own JWKS, so a revoked consent stops refreshes immediately but an issued access token stays valid until it expires; access tokens are therefore short-lived.
- `/api/mcp` is authorized by bearer token, not the session cookie. The proxy must let it through so the route can answer 401 with the `WWW-Authenticate` challenge MCP clients need for discovery; every other `/api` path keeps the cookie gate.
- The MCP route is stateless (one request per call, no protocol sessions), which suits Vercel functions and needs no Redis.
- Route handlers stop owning authorization and read-time behavior such as recurring Expense materialization; they parse HTTP, call the operations module and map its errors. This is useful without MCP and is the first delivery step.
- MCP is off unless enabled per deployment; demo personas can authorize an assistant locally, and production keeps demo auth blocked.

## Update: 19 October 2026

This dated update supersedes conflicting proposals above without rewriting the 1 October history or accepting every part of the original design. Authority: [ADR 0008](0008-persistent-assistant-expense-drafts.md), [spec #383](https://github.com/FireBird1998/splitbook/issues/383) and its [19 October amendment #603](https://github.com/FireBird1998/splitbook/issues/603), covering the owner's Q16–Q24 decisions. See [Connected assistants](../connected-assistants/README.md) and its [decision comparison](../connected-assistants/decisions.md) for the disposition of the unmerged 4 October PR #242.

- The server remains a stateless route in the existing web app, with bearer authorization, metadata discovery and member identity through Better Auth. Client ID Metadata Documents identify clients; the chosen rollout keeps dynamic client registration off. Code retains an off-by-default compatibility flag, not a rollout exception.
- Disconnect is immediate through a live grant/generation check on every call and at token issuance. This replaces the original short-lived-token-only proposal: a valid signature does not preserve access after revocation. A request authorized before revocation may finish; completed effects are not undone.
- Optional To review permission allows reading, preparing, revising and permanently discarding the member's private Expense Drafts. Ledger-only access never exposes them. Only the member saves Expenses in Splitbook review; there is no assistant save tool or authority to mutate saved Expenses, Settlements or Group data. ADR 0008 replaces the temporary preview/record direction for Expense preparation.
- Chosen Group access is current membership minus the connection's Excluded Groups minus Groups whose Assistant rule is Not allowed. All Groups start ticked at approval, and Groups joined later are included. Per-assistant Group edits apply at once without reconnecting; To review access changes require reconnecting.
- Every tool, including Draft tools, must apply that Group access check on each call. Unreachable Groups are absent from results and indistinguishable from nonexistent Groups by id. Only admins change the Assistant rule (Allowed by default); changes add Activity naming the admin/new rule and keep existing Drafts. Members see the rule; admins additionally see member/assistant/last-used reach information.
- Connections unused for 90 days expire and appear as gone. Last used is updated on authorized calls at most once a minute; token lifetimes must not shorten the chosen idle period. This is connection expiry, not automatic Draft expiry.
- Connecting and approving is opt-in; the proposed private-beta member switch is superseded. Keep the deployment-wide switch. Approval names the assistant, lists Groups with a leave-out warning and separate To review access, and explains limits. Settings shows name, access, reach and last used; Disconnect requires confirmation.
- Production waits for Excluded Groups, the Assistant rule, approval, Settings controls and idle expiry, with staging acceptance and owner approval. ChatGPT/Claude/Other setup, help and Android connection-management scope follow #603; Claude/Other setup, help and the Android screen may follow production. The 4 October insight tools, tool switches, call log and approvals queue are not in this scope.

**Implementation status, 21 October 2026 (#615/#618):** OAuth/metadata support, ledger reads, optional Draft tools and live revocation checks exist. Settings lists assistant names, addresses, server-reported access and last use, and requires confirmation before Disconnect. Last use is recorded on authorized calls at most once a minute; a failed timestamp write logs and retries on the next call without denying authorized access. Server-enforced 90-day inactivity expiry applies to MCP calls, token issuance and the Settings list. Five-minute access tokens retain live checks; refresh tokens roll forward for 91 days so their lifetime cannot shorten the idle window. A staging-only timeout has a 120-second floor, is ignored on the production deployment and, if malformed, logs once per server instance and disables only MCP (503) at initialization, leaving normal sign-in and app pages available. An unset or empty timeout keeps 90 days. Group access remains membership-only in these tickets; approval and Group controls are separate work. Current assistant reads do not materialize recurring Expenses. Production readiness still requires the remaining controls and hosted acceptance. See [implementation evidence](../connected-assistants/research.md) and the [connection runbook](../runbooks/mcp-connections.md).

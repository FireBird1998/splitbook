# Production database backups

During the beta, production's database is backed up by a nightly job on the owner's Mac, not by Atlas: a free cluster has no backups ([ADR 0011](../adr/0011-separate-databases-least-privilege-self-run-backups.md)). The scripts are in `tools/db-backup/`.

## What runs

- **When:** 03:30 local time, by launchd (`in.splitbook.backup`). A Mac that is asleep then runs the job when it wakes; a Mac that is off misses it.
- **Who connects:** `splitbook_backup`, an Atlas database user with `read` on production's database (`splitbook`) and nothing else. Its password is in the login Keychain (service `splitbook-backup`, account `splitbook_backup`). It never appears on a command line or in a file that outlives the run.
- **Where:** `~/SplitbookBackups`, which only the owner can read, on a FileVault-encrypted disk.
  - `backup.env`: the connection string without a password, the database, the Keychain item and how many dumps to keep.
  - `bin/`: the installed copies of `backup.sh` and `restore-check.sh`.
  - `dumps/<UTC time>/`: one gzipped `mongodump` of the database, its `manifest.tsv` (each collection and its documents) and `mongodump.log`. The newest 14 are kept.
  - `logs/backup.log`: one `OK …` or `FAILED …` line per run. A failure also shows a macOS notification and leaves a `.partial-…` folder to look at.
- **Each run checks itself:** every collection's documents are read back from the dump and must equal what `mongodump` reported. A dump that doesn't read back is never counted as a backup.

Dumps hold the members' data. Never commit them, attach them to an issue, or copy them anywhere unencrypted.

## Is it working?

```sh
tail -n 5 ~/SplitbookBackups/logs/backup.log
ls ~/SplitbookBackups/dumps
```

To run it now, outside the schedule:

```sh
launchctl kickstart "gui/$(id -u)/in.splitbook.backup"
```

## Prove a dump restores

Restore a dump into a throwaway local MongoDB (Docker, `mongo:8.0`), count every collection, compare with the manifest, then remove the throwaway database. Nothing touches Atlas.

```sh
~/SplitbookBackups/bin/restore-check.sh                      # the newest dump
~/SplitbookBackups/bin/restore-check.sh ~/SplitbookBackups/dumps/<UTC time>
```

Do this after setting it up, and now and then. The first production dump (22 October 2026: 21 collections, 192 documents) matched Atlas's own counts for every collection.

## Restore production from a dump

Only the owner does this, with the admin user. **Never restore over production's database.** Restore beside it, check, then point the app at it.

1. **Keep what's there.** Run a backup of the current state first, even if it's damaged: `launchctl kickstart "gui/$(id -u)/in.splitbook.backup"`.
2. **Restore into a new database** on the production cluster, named for the day. `mongorestore` asks for the password.

   ```sh
   mongorestore --uri='mongodb+srv://<admin user>@<cluster host>/?authSource=admin' --gzip \
     --nsInclude='splitbook.*' --nsFrom='splitbook.*' --nsTo='splitbook_restored_<yyyymmdd>.*' \
     ~/SplitbookBackups/dumps/<UTC time>
   ```

3. **Check it** in Atlas's Data Explorer: the collections and counts match the dump's `manifest.tsv`, and the Group is there.
4. **Switch the app over.**
   - Give `splitbook_app` `readWrite` on the new database.
   - Change the path of production's `MONGODB_URI` in Vercel to the new database's name.
   - Redeploy production.
   - The damaged database stays untouched for as long as it's needed.

To restore a single collection instead, use the same command with `--nsInclude='splitbook.<collection>'`, still into a new database, and copy the documents you need from there.

## Set it up on a Mac

1. **Install the tools:** `brew tap mongodb/brew && brew install mongodb/brew/mongodb-database-tools`. Docker is needed for `restore-check.sh`.
2. **Create the user:** in Atlas, open the production project, then Database Access → Add New Database User.
   - Username `splitbook_backup`, with an autogenerated password.
   - Under Specific Privileges, add `read` on `splitbook`.
   - **Remove the Built-in Role** "Read and write to any database", which Atlas selects by default.
3. **Store the password:** `security add-generic-password -s splitbook-backup -a splitbook_backup -w`, then paste it at both prompts. Use `-U` to replace an existing one.
4. **Install:** from the repository, `tools/db-backup/install.sh <cluster host> splitbook`. The host is the `mongodb+srv://` address's host in Atlas's Connect dialog.
5. **Check:** run `~/SplitbookBackups/bin/backup.sh`, then `restore-check.sh`.

To stop the nightly job: `launchctl bootout "gui/$(id -u)/in.splitbook.backup"`, then delete `~/Library/LaunchAgents/in.splitbook.backup.plist`.

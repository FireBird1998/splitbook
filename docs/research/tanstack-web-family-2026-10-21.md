# TanStack alongside Next.js: platform and removal evidence

Research for [Research: Next.js-compatible TanStack libraries and platform limits](https://github.com/FireBird1998/splitbook/issues/705), under [Wayfinder: TanStack adoption alongside Next.js, with Android first](https://github.com/FireBird1998/splitbook/issues/702). Checked 2026-10-21 against baseline `ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95`. Recommendations below are inferences, not adoption decisions. Next.js stays; Android maintenance reduction takes priority. No packages were installed and no runtime compatibility or bundle measurements were performed.

## Existing owners constrain useful adoption

[ADR 0006](../adr/0006-android-client-architecture.md) is authoritative: Android Query owns display reads headlessly inside the controller; the snapshot owns client state and Drafts; forms remain controller-owned; financial writes stay explicit, online and outside mutations. Web retains SWR. Shared domain code stays framework-free. Query adoption on Android is complete enough that the current controller imports `QueryClient`, `QueryObserver`, `focusManager` and `onlineManager`; it sets `retry: false` and `networkMode: 'always'`. Its [query-owner module](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/data/query-owner.ts) contains response-owner/invalidation safeguards that a new UI adapter must preserve.

**Inference:** Form is the only surveyed UI candidate with explicit first-party React Native guidance and a plausible Android form-maintenance target. That establishes research priority, not permission to put a second writable copy of a Draft in screens. Hotkeys is a bounded web-only possibility. Table, Virtual and Charts need evidence of current complexity or measured performance costs before migration. Retaining SWR is the default outcome.

## Hotkeys: a matching engine, not a focus engine

Official APIs include `useHotkey`, `useHotkeys`, `HotkeysProvider`, targets, `enabled`, `ignoreInputs`, `requireReset` and duplicate conflict policy. Default input handling is `auto`, repeat is allowed (`requireReset: false`), and both default prevention and propagation stopping default on. `Mod` chooses Meta on macOS and Control elsewhere. [Registration/options](https://tanstack.com/hotkeys/latest/docs/framework/react/guides/hotkeys). Named scopes follow the React tree, including portals; targets follow DOM focus, and nested scopes win. [Scopes](https://tanstack.com/hotkeys/latest/docs/framework/react/guides/hotkeys-provider-and-scopes). App declarations can centralize shortcut metadata and bindings, while persistence stays with the application. [App hotkeys](https://tanstack.com/hotkeys/latest/docs/framework/react/guides/app-hotkeys).

Current behavior is defined by [`shortcuts.ts`](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/web/src/lib/shortcuts/shortcuts.ts), [`ShortcutsProvider.tsx`](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/web/src/lib/shortcuts/ShortcutsProvider.tsx), [`shortcut-setting.ts`](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/web/src/lib/shortcuts/shortcut-setting.ts), [`expense-table-keys.ts`](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/web/src/components/expenses/expense-table-keys.ts) and [`SearchLauncher.tsx`](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/web/src/components/search/SearchLauncher.tsx):

- All dispatch rejects IME composition. Ordinary text fields suppress **even Cmd/Ctrl+K**; the search field itself permits it to close search. Single keys additionally reject editable ARIA widgets and open dialogs, menus or listboxes. Cmd/Ctrl+K has a different overlay policy from single keys.
- Search accepts exactly one of Meta or Control on **any** platform, rejects Alt/Shift, and currently permits repetition. `Mod+K` alone would narrow that contract. Letters allow Shift; single keys reject Ctrl/Alt/Meta.
- N, slash and E ignore repeat; J/K repeat to move. Enter remains the row button's native activation and never enters the custom dispatcher.
- The newest non-fallback handler wins, otherwise the newest fallback. The slash fallback routes to a Group's Expenses through Next navigation and hands focus intent to the next real handler once, within ten seconds. An Expenses page whose search failed stays put.
- The single-key preference is per member/device, synchronized across tabs, unknown/off during hydration, default-on after reading, with in-memory survival when storage fails. Hints and `aria-keyshortcuts` follow it.
- J/K query Expense rows, clamp at the ends, focus the button with `preventScroll`, then scroll nearest; E edits the focused or open Expense. Every row button remains in Tab order.

**Inference/removal test:** a prototype could replace low-level registration/listener and chord matching, potentially hint formatting. It must retain or explicitly replace the product guards, preference adapter, fallback priority, route handoff and row-focus/scroll code. Scopes do not automatically reproduce DOM overlay detection or fallback semantics. Do not assume automatic conflict handling picks the existing winner. Run the existing shortcut and browser cases unchanged, including IME, both Ctrl/Meta on either platform, Shift letters, search-field exception, held keys, portals, failed search mounts, delayed navigation and member switches. Demonstrate fewer production lines/modules after adapters; otherwise keep the small existing engine. Roll back by restoring the existing provider with unchanged call sites and storage keys. No financial writes belong in shortcut infrastructure.

Hotkeys' default targets and keyboard events are DOM concepts; its React DOM peer is additional evidence against treating it as an Android keyboard/navigation solution. No native focus or accessibility replacement is established here.

## Form

Stable v1 documents `useForm`/field state and validators; the React Native example wires `TextInput.onChangeText` to `field.handleChange` and renders errors with native `Text`. This is explicit native guidance, stronger than a generic React claim, but not an on-device Hermes result. [Native guide](https://tanstack.com/form/latest/docs/framework/react/guides/react-native). Next integration offers `@tanstack/react-form-nextjs`, shared `formOptions`, server validation and client merging; it does not require changing routers. [SSR guide](https://tanstack.com/form/latest/docs/framework/react/guides/ssr).

**Inference:** prototype one existing Android Expense form only after an owner decision reopens ADR 0006's no-form-library choice. One owner must hold field values/dirty/touched/errors; eliminate the corresponding custom field machinery rather than synchronizing two stores. Keep Draft recovery, account cleanup, validation copy, allowed save-state transitions, immutable retry identity/revision and online save commands in their existing owners. `handleSubmit` may call the explicit command; the library's submit state cannot become persisted financial-save state. Web may use stable v1 in client components without adopting server actions or changing HTTP endpoints. Measure deletion of validation plumbing separately from retained domain validation. Prototype native blur/error/focus, reopen/recovery and account switches; reject if bridges increase production code or renders. Roll back the UI field adapter without changing Draft storage/schema. Form 2 alpha is unnecessary for this question.

## Table and Virtual

Table **v9 is current stable**, not the older v8 snippets commonly found in searches. Its quick start uses `useTable` with explicit features; it is a headless state/row-model engine, compatible with MUI while leaving markup and styling to the application. [Overview](https://tanstack.com/table/latest/docs/overview), [v9 quick start](https://tanstack.com/table/latest/docs/framework/react/quick-start). The current `ExpenseTable.tsx` is an accessible semantic table with owned row activation, day headings and side-panel state; there is no demonstrated complex grid-state engine to delete. **Inference:** defer Table. Adopt only if a measured prototype removes current sorting/filtering/pagination orchestration without moving server pagination or domain grouping into a second owner. Table core being framework-independent does not supply Android cells, focus, native lists or a Hermes guarantee.

Virtual exposes `useVirtualizer`, a scroll element, estimated sizes and measured visible items; it renders no markup. Its official example uses a DOM `div` and manually positioned items. [Virtual introduction](https://tanstack.com/virtual/latest/docs/introduction). **Inference:** web-only performance option when measurements warrant it, independent of Table. It adds measurement and focus-retention obligations and does not replace native `FlatList`. Follow existing [Android: measure frames, jank and memory on a low-end phone](https://github.com/FireBird1998/splitbook/issues/194), [Android: move long lists to FlatList only if the memoized build misses the device budget](https://github.com/FireBird1998/splitbook/issues/179), and [Android: re-measure frames, jank and memory on the low-end phone after the migration](https://github.com/FireBird1998/splitbook/issues/226) work and ADR 0006's memoized rows → FlatList → FlashList gates. A web prototype must preserve focused/open rows, J/K to unmounted rows, semantic headings, sticky offsets and return anchors; roll back by rendering the full existing row collection. No virtualization prototype is justified merely by package availability.

## Query and debugging

Query v5 works in React Native, with explicit AppState/online integration; native debugging options listed by TanStack are third-party tools. [Native Query guide](https://tanstack.com/query/latest/docs/framework/react/react-native). Retain Android's existing core ownership and custom saved-copy persister. Adding React hooks solely for Devtools would introduce another interface without deleting the controller seam.

Next App Router support uses a client `QueryClientProvider`, per-request server clients and dehydration/`HydrationBoundary`; interactive hooks belong behind client boundaries. [Advanced SSR](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr). **Inference:** technically compatible with retained Next, but web migration would reopen ADR 0006's explicit SWR choice and its earlier size/defaults comparison. Candidate removals are SWR hooks/provider and invalidation wiring, not API handlers, retry identity or account/access cleanup. Never give SWR and Query ownership of the same resource during coexistence. Require current bundle/request comparisons, account isolation and delayed-response tests before an owner decision. Do not repeat historical byte estimates as current measurements.

The generic Devtools shell is alpha and has a Solid-based UI, React DOM peers and an optional **Vite** build plugin. [Architecture/status](https://tanstack.com/devtools/latest/docs/overview). Next's webpack build cannot simply use the Vite plugin's production stripping. Browser Query/Form/Hotkeys/Table panels are development-only candidates once their corresponding engine exists, with explicit production exclusion and data-redaction review. None is evidence that the same panel runs natively. No custom debug panel maintenance was identified that these immediately remove.

## Remaining family: explicit screening

The [official library navigation](https://tanstack.com/devtools/latest/docs/overview) also lists DB, Store, AI, Charts, Markdown, Highlight, Pacer, Config, CLI and Intent; Ranger remains available. Registry `latest` checks: [react-db 0.5.11](https://registry.npmjs.org/@tanstack%2freact-db), [react-store 0.11.2](https://registry.npmjs.org/@tanstack%2freact-store) (1.0.0-alpha.0 separately), [react-pacer 0.24.1](https://registry.npmjs.org/@tanstack%2freact-pacer), [react-charts 1.1.0](https://registry.npmjs.org/@tanstack%2freact-charts), [ai 0.70.0](https://registry.npmjs.org/@tanstack%2fai), [cli 0.72.0](https://registry.npmjs.org/@tanstack%2fcli), [config 0.22.2](https://registry.npmjs.org/@tanstack%2fconfig), [intent 0.5.6](https://registry.npmjs.org/@tanstack%2fintent), [react-ranger 0.0.5](https://registry.npmjs.org/@tanstack%2freact-ranger).

**Screening inferences:** DB/Store/Pacer need the separate ownership and scheduling research in this map; no second read/Draft owner or automatic write queue is licensed here. Charts could replace existing MUI charts only if it removes maintenance; React DOM peers do not establish native chart rendering. [Charts](https://tanstack.com/charts/latest). AI is model/chat infrastructure, whereas Splitbook's Connected assistant is an existing authorization/API contract: no new in-app model demand was found. [AI](https://tanstack.com/ai/latest). Markdown/Highlight render rich text/code; Ranger concerns range controls: no existing replacement target was identified. [Markdown](https://tanstack.com/markdown/latest), [Highlight](https://tanstack.com/highlight/latest), [Ranger](https://tanstack.com/ranger/latest). Those first two product pages exist, but the guessed `@tanstack/react-markdown` and `react-highlight` registry names return 404: do not invent published coordinates. Workflow's guessed package/page likewise did not establish a usable released package. CLI/Config/Intent are tooling candidates, not app-state migrations; replacing working pnpm/Next/swarm configuration has no proven reduction. Router/Start remain out of scope regardless of their published stable channels.

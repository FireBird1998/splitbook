## Recommendation

Yes, React Query (TanStack Query) fits the app's server-read lifecycle. It can support showing previously loaded data while refreshing, per-resource freshness, and clearer initial-load versus refresh state. It will not independently fix duplicate loader rendering or the app's financial consistency rules. First correct the loading presentation and refresh orchestration in the existing controller; then migrate one read domain at a time if the team wants a standard cache lifecycle. Keep drafts, authentication, and immutable financial submission recovery in their current dedicated stores. This is an architectural recommendation, informed by the code findings and official behavior below, not an existing implementation.

## What the code currently does

- The read cache is **network-first fallback**, not stale-while-revalidate. `readCached` tries the request and saves validated data; only a transport failure opens the persisted cached response. A request has a 20-second timeout. Thus the presence of an offline cache does not make normal navigation or refresh immediately display saved data. [Controller: `request` and `readCached`](../../apps/mobile/src/data/mobile-controller.ts)
- `refreshHome` and `refreshBalances` clear their data on load. `openGroup` resets financial state; a non-pagination expense refresh also replaces the expense state. `App.tsx` makes native `RefreshControl.refreshing` true whenever any relevant section is loading, while `FinancialState` renders section spinners. This explains how one refresh can produce multiple loaders and blank sections; it is a code-level explanation, not a measured device trace. [App](../../apps/mobile/App.tsx), [controller](../../apps/mobile/src/data/mobile-controller.ts), [financial views](../../apps/mobile/src/ui/financial-views.tsx)
- Foregrounding calls `controller.refresh()` on every `AppState` transition to `active`. Opening a Group reads Group context, then expenses, then balances. The sequence has a reason: the expense GET materializes due recurring entries; `beginExpenseRead` invalidates Home and Group balances before it runs. Unconditionally fetching balances in parallel with expenses could display a balance from before those entries. [Controller](../../apps/mobile/src/data/mobile-controller.ts), [expense route](../../apps/web/src/app/api/groups/[id]/expenses/route.ts)
- Cache storage uses SQLite records scoped by environment and account, with response paths inside the account document. Saved responses carry account, path, and refresh time. The controller uses account generations, serialized storage leases, and a cache epoch to reject obsolete work; it removes Group cache on access denial and runs account cleanup on sign-out/account changes. These are existing protections to preserve, not capabilities supplied automatically by a new cache library. [Storage](../../apps/mobile/src/data/account-record-storage.ts), [read store](../../apps/mobile/src/data/read-cache-storage.ts), [cache validation](../../apps/mobile/src/data/offline-cache.ts), [controller](../../apps/mobile/src/data/mobile-controller.ts)
- ADR 0004 allows labeled offline viewing and durable drafts but requires online financial writes. Lost-response recovery retains the exact attempted payload and retry identity separately from an editable draft; conflicting edits require review. Household month selection applies to expenses; running balances remain all-time. [ADR 0004](../adr/0004-expo-mobile-client.md), [controller](../../apps/mobile/src/data/mobile-controller.ts), [financial views](../../apps/mobile/src/ui/financial-views.tsx)

Inactive queries default to five-minute garbage collection, and failed queries default to three retries with backoff. | Set a deliberate freshness and retry policy. Merely installing the library can preserve frequent requests. `staleTime` concerns freshness; `gcTime` concerns retention. ## Low-risk stages

1. **Fix feedback without changing cache ownership.** Separate `hasData`, request activity, request origin (`initial`, `manual`, `background`, `pagination`), freshness, and last refresh error. Keep matching data visible during refresh. Use native pull-to-refresh feedback only for a pull gesture; use one quiet refresh indicator for automatic refresh. Reserve a full loading placeholder for a genuinely empty first load, and a footer for pagination. A failed background refresh should retain data with its old timestamp and a retry affordance. After an expense read begins, retained balances must be labeled as previous/unverified until the ordered balance refresh finishes; retaining the number must not claim it is current. This recommendation addresses the specific state resets and duplicate indicator paths described above.
2. **Improve read reuse inside the controller.** Introduce one resource identity and one in-flight read per identity, with a short freshness window and explicit invalidation after confirmed writes. A proposed starting point is 30 seconds for ordinary foreground reads, subject to device/network measurement; manual refresh and confirmed writes bypass that window. Hydrate matching, validated saved data before revalidation, preserving its original timestamp. Account and membership checks remain independent of whether financial data is considered fresh. Do not change the expenses-before-balances dependency merely to shorten a request waterfall.
3. **Pilot Query for one bounded read.** Activity is a candidate after confirming all its write-invalidation dependencies; it avoids beginning with the coupled expense/balance flow. Move that resource's fetching, in-memory state, and invalidation to Query together. The controller may retain navigation and authorization responsibilities, but must stop independently refreshing or caching the same resource. Use the pilot to compare warm navigation, foreground refresh, offline errors, and request counts with stage 2. This is an incremental architecture change, not a prerequisite to fixing the loaders.
4. **Migrate the coupled ledger reads only after the pilot.** Preserve explicit orchestration: verify Group access, fetch expenses/materialize recurring entries, then fetch all-time Group balances; refresh Home aggregates when appropriate. Invalidate every affected month/page and aggregate after confirmed create/edit/delete/settlement outcomes. Keep a coherent prior snapshot labeled stale until replacements are safe to publish. Drafts, conflict review, and unresolved attempts remain outside Query.

Improving the controller alone has the smallest immediate migration risk, but the team continues maintaining freshness, deduplication, persistence, and retry semantics. Incremental Query adoption standardizes those read concerns while introducing adapter and account-lifecycle work. A full controller rewrite combines both risks and is not recommended for the loader problem.

## Cache ownership, persistence, and account boundaries

**Recommendation:** Never simply wrap `readCached` in a query function. A fallback response currently resolves successfully; Query could then treat old offline data as a new successful response with a misleading refresh timestamp. Keeping two independently writable caches also creates ambiguous invalidation and sign-out cleanup. Extract a network-only validated read function, then choose one owner for each migrated resource. Existing SQLite can remain a persistence backend, provided a defined adapter preserves timestamps, account scope, validation, and deletion ordering.

Suggested key shapes are `['native', environment, accountId, 'group', groupId, 'expenses', filters]` and `['native', environment, accountId, 'group', groupId, 'balances']`. Expense filters include the month or actual local date boundaries, page/cursor, limit, and member-breakdown mode. Balances have no month key. Never display the previous account, Group, or month's data as a placeholder for a new identity. These are app-specific recommendations based on the key rules and current month behavior cited above.

TanStack supplies asynchronous persisters, including a React Native AsyncStorage adapter. Persistence is an added integration, not a consequence of the in-memory cache. [Async storage persister](https://tanstack.com/query/latest/docs/framework/react/plugins/createAsyncStoragePersister)

`PersistQueryClientProvider` coordinates restoring and fetching. Its persistence options include expiration and a cache buster; documentation says `gcTime` should be at least the selected persistence `maxAge`. **Recommendation:** explicitly choose retention, schema version, and an environment/account-specific storage key. Reuse the existing SQLite storage lifecycle where practical instead of introducing another financial-data store. [Persistence](https://tanstack.com/query/latest/docs/framework/react/plugins/persistQueryClient)

**Recommendation:** On sign-out, session denial, or account change: stop rendering the old account, advance its generation, cancel reads, stop persistence subscriptions and drain/invalidate pending writes, clear memory and persisted account data, then allow another account to hydrate. Group-level denial removes that Group plus dependent Home summaries; it is not automatically a global sign-out. Preserve the existing cleanup marker and fail-closed behavior. Cancellation/removal/clear APIs are available, but this sequencing and storage cleanup remain application responsibilities. [QueryClient API](https://tanstack.com/query/latest/docs/framework/react/reference/classes/QueryClient), [current account cleanup](../../apps/mobile/src/data/mobile-controller.ts)

**Recommendation:** Persist display reads only; explicitly set `shouldDehydrateMutation: () => false` when using dehydration, and do not call `resumePausedMutations`. Keep financial mutation `retry: false` and explicit connectivity/authorization checks; neither that retry setting nor `networkMode: 'online'` alone guarantees no paused mutation will execute later. The lowest-risk pilot keeps all writes outside Query. Any future write integration must retain the immutable serialized body, idempotency key, revision precondition, and user-triggered recovery. The dehydration predicate is an official API; excluding every mutation is this app's policy. [DehydrateOptions](https://tanstack.com/query/latest/docs/framework/react/reference/interfaces/DehydrateOptions), [ADR 0004](../adr/0004-expo-mobile-client.md)

## Verification gates before rollout

These are proposed acceptance criteria, not completed tests:

- Warm same-resource navigation keeps data visible; only actual first loads use a blocking placeholder. Pull refresh shows one primary progress cue; background refresh does not trigger the native pull indicator.
- Foreground/reconnect events coalesce, do not duplicate a read already running, and never submit an Expense or Settlement. Offline cache misses settle into an actionable state. Network detection is advisory; failed requests still determine actual reachability.
- Month/page switching never mislabels prior expenses and never filters all-time balances. Recurring materialization cannot allow a pre-materialization balance to overwrite a newer one.
- Background failure retains matching data with an honest timestamp. A new account or denied Group immediately loses access to old data, including after restart and with a late response or delayed persistence write.
- Editing during a background refresh preserves the draft. Lost-response retries send the original body/key; changing the draft cannot mutate the attempted submission. No restart/reconnect path replays financial writes automatically.
- Compare cold and warm screen timings, blank-content duration, simultaneous loaders, and request counts on a device under ordinary, slow, offline, and reconnect conditions. Do not claim a latency improvement from changing libraries until those measurements exist.

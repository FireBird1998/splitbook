# Android data ownership and timing after Query

Research for [Research: TanStack Query, Pacer and DB boundaries on Android](https://github.com/FireBird1998/splitbook/issues/704), under [Wayfinder: TanStack adoption alongside Next.js, with Android first](https://github.com/FireBird1998/splitbook/issues/702), checked **2026-10-21**. This is evidence for an owner decision, not adoption approval. Keep Next.js, prioritize Android, preserve existing behavior, and judge proposals by custom code removed. No application changes or native execution were performed.

## Current baseline and retained contracts

The inspected repository baseline is `ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95`. Android already depends on Query core: manifest `^5.104.1`, lockfile **5.104.1**. It uses Expo `~57.0.25`, React Native **0.86.3**, React **19.2.3**, and expo-sqlite `~57.0.3`. Repeating the Query migration would solve an obsolete problem. The current implementation has `QueryObserver` and `InfiniteQueryObserver`, 5-page windows, structural sharing, observer-driven activation, custom saved-copy envelopes and separate persistence queues. [Manifest](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/package.json), [lockfile](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/pnpm-lock.yaml), [Group reads](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/data/group-queries.ts).

The accepted boundaries remain controlling:

- Query owns Android display reads inside the controller. Screens subscribe to its snapshot. No Query mutations; financial saves are explicit, online operations. Store attempted payload and idempotency key/revision before sending; retry unchanged, only when the member requests it.
- A saved copy retains its original verification time and never becomes fresh because it was restored. Reads use `retry: false`, `networkMode: 'always'`, 30-second live freshness and zero saved-copy freshness. Connectivity is classified by transport, including stalled bodies; cancellation is distinct from offline.
- Account and environment isolate queries and disk rows. Sign-out/account change wait for strict financial storage work, stop pending saved-copy work and purge account-local records. A 401 clears memory/credentials without treating disk recovery as signed-out-account data that can be shown to someone else.
- Device-local recovery, server Draft collections and ledger Expenses are distinct. Reconnection never uploads a Draft automatically; saving multiple Drafts retains independent outcomes and uncertain replies. Shared domain code remains framework-free.

These are requirements, not library defaults. See [ADR 0002](../adr/0002-shared-domain-package.md), [ADR 0004](../adr/0004-expo-mobile-client.md), [ADR 0006](../adr/0006-android-client-architecture.md) and [ADR 0008](../adr/0008-persistent-assistant-expense-drafts.md). Current source evidence includes the controller's Query defaults and `accountStorage` lease, `Envelope` and `createSavedCopyQueue` in Home reads, and distinct SQLite tables/files for saved queries, Draft recovery, Settlement attempts, Group creation, Draft requests, Tag requests and pending sign-out. [Controller](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/data/mobile-controller.ts), [Home reads](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/data/home-queries.ts), [SQLite records](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/data/account-record-storage.ts).

## Remaining Query simplification

The largest remaining opportunity is consolidation of app adapters, not another cache engine. Home, Group, Expense and Activity modules repeat saved-row loading, network-only fallback, write scheduling, session checks, provenance and observer projection. A small internal saved-read adapter could remove repeated mechanics while retaining resource-specific access, invalidation and display rules. Keep wire JSON plus provenance as the cache value; do not introduce a second normalized store merely to reuse functions. Compare the current [Expense](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/data/expense-queries.ts) and [Activity](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/data/activity-queries.ts) adapters.

Infinite Query already supplies page-direction fetching and `maxPages: 5`; loaded-window refresh and older/newer navigation are therefore maintenance of an adopted feature. A replacement must retain per-page verification provenance and the sliding window, not silently load a whole Group. Query cancellation passes an AbortSignal when consumed, but Splitbook deliberately distinguishes the lifetime of a cached query from the current screen. Removing the last observer is not automatically permission to abandon an otherwise valid response. The app's query-owner checks reject a removed query's late network answer or deferred disk write, even if a successor has the same key. Do not delete these guards simply because Query supports cancellation. [Infinite query guide](https://tanstack.com/query/latest/docs/framework/react/guides/infinite-queries), [cancellation guide](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation), [ownership source](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/data/query-owner.ts).

Stock persistence remains unsuitable. It does not supply this account lease, original verification-time semantics, distrust after failed removal, protected Home/open-Group budget policy, or the strict distinction between write recovery and expendable saved copies. Dehydration options can exclude mutations, but that alone cannot establish these guarantees. Preserve the custom boundary unless a prototype demonstrably replaces every contract, including delayed persistence after sign-out. [Persistence guide](https://tanstack.com/query/latest/docs/framework/react/plugins/persistQueryClient), [hydration API](https://tanstack.com/query/latest/docs/framework/react/reference/hydration).

## Pacer: useful timing, wrong durability abstraction

Current production timers are small and concrete: transport's 20-second whole-request timeout and one-second denial-body allowance; a delayed Draft saving indicator; snackbar dismissal; deferred input focus; and scroll-anchor settling on Expense, Activity and history views. There is no large home-grown debounce/search scheduler to remove. Cancellation, timeout classification and denial cleanup in transport remain application correctness logic. Replacing a `setTimeout` and its cleanup with a reactive scheduler could increase maintenance. [Transport](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/data/transport.ts), [Draft indicator](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/ui/draft-status.tsx), [list anchor](https://github.com/FireBird1998/splitbook/blob/ef4f1b9cd3e1db7cd0807c1281983c2947dc5b95/apps/mobile/src/ui/group-expenses.tsx).

Pacer 0.23.1's published AsyncQueuer defaults to concurrency one and one attempt, but supports retries, abort, priority, expiry and start/stop. Its scheduler operates on JS objects and timers. Initial state or a storage callback is not an atomic durable save journal. Stopping pending work also does not roll back an already transmitted request or revoke a stale account lease. [Published AsyncQueuer](https://unpkg.com/@tanstack/pacer@0.23.1/dist/async-queuer.js), [Queuer](https://unpkg.com/@tanstack/pacer@0.23.1/dist/queuer.js), [Debouncer](https://unpkg.com/@tanstack/pacer@0.23.1/dist/debouncer.js).

Two queues must stay distinct. The strict promise chain behind `accountStorage.write` preserves ordered Draft/attempt work and checks generation/account at execution time. It is not an automatic network replay queue. `createSavedCopyQueue` is only about optional disk copies: a pending write is replaced by the latest for its query key, `drop(key)` removes pending work, `cancel()` clears pending work, and `idle()` waits for already admitted work. That helper is roughly thirty lines. A generic FIFO/priority queue still needs keyed replacement, lease checks, retirement and purge ordering. There is no demonstrated net deletion from replacing it with Pacer.

Therefore defer Pacer unless a measured timing use case appears. An isolated prototype could compare one repeated scroll-settle timer utility with Pacer, preserving disposal/background behavior and deleting more custom code than it adds. Never wrap ledger saves, recovery persistence, or shared Draft saves in an auto-starting/retrying scheduler.

## DB: native persistence exists; a useful ownership role is unproven

DB offers normalized collections and live queries over them. That could help a future read-only join across independently loaded resources. It does not replace the MongoDB backend, financial validators or server Balances with authoritative local aggregates. Current Group views expose bounded pages; absence from a page is not absence from the ledger. Eagerly loading a collection changes behavior and resource cost, while on-demand mode needs a mapping from collection predicates to existing API endpoints. [DB overview](https://tanstack.com/db/latest/docs/overview), [published DB README](https://unpkg.com/@tanstack/db@0.15.1/README.md), [Query collection](https://tanstack.com/db/latest/docs/collections/query-collection).

Native persistence is more capable than a browser-only assessment suggests. The first-party Expo wrapper uses the official async expo-sqlite API, and its published README names Android emulator and iOS simulator test paths. Its peer range includes the app's Expo SQLite generation. The separate React Native wrapper uses OP-SQLite; choosing that wrapper is unnecessary here. This removes one compatibility objection, not the ownership problem. Upstream test commands are evidence of intended coverage, not proof that Splitbook's Hermes build, shutdown, account cleanup and concurrent writes work. [SQLite guide](https://tanstack.com/db/latest/docs/guides/sqlite-persistence), [published Expo wrapper README](https://unpkg.com/@tanstack/expo-db-sqlite-persistence@0.2.36/README.md), [published wrapper metadata](https://unpkg.com/@tanstack/expo-db-sqlite-persistence@0.2.36/package.json).

Adding Query Collection plus DB persistence would otherwise create three retained representations: Query envelopes, normalized collection rows and existing saved query rows. A proposal must name exactly one owner of fetching, verification time, retirement, hydration and projection, then delete the redundant representation. DB's local persistence and offline transaction replay are separate features. Neither automatic optimistic financial mutations nor replay is acceptable; read-only collections must have no path that resumes a ledger save. LocalStorage/IndexedDB browser adapters are not substitutes for the SQLite account protocol. [SQLite lifecycle](https://tanstack.com/db/latest/docs/guides/sqlite-persistence), [offline transactions](https://tanstack.com/db/latest/docs/guides/offline-transactions).

## Small proofs and rollback boundaries

1. **Query adapter consolidation:** prototype one repeated saved-read path without changing controller commands or snapshot. Count deleted production lines after accounting for the adapter, and preserve request/render ceilings. Exercise saved-copy restart with original times, cancellation versus offline, removal followed by a same-key late answer, account switch and failed purge. Roll back by restoring the existing module; no disk schema change.
2. **Pacer only if justified:** prototype one nonfinancial timing surface with the exact package version. Prove Android Hermes/Metro compatibility, teardown and background behavior, callback/error parity and bundle cost. Reject if the adapter equals or exceeds the removed timer code. Roll back by restoring the timer helper; persist no scheduler state.
3. **DB only for a demonstrated read-model need:** before implementation approval, show a read-only collection behind the existing snapshot with an ownership diagram and exact deletion inventory. Test Expo SQLite restart, account-scoped teardown, original verification times, stale-copy distrust, page-window semantics and absence of replay. Use a separate disposable derived database; old saved copies remain available for rollback and financial recovery schemas are untouched. Reject if this leaves two long-lived read owners or needs API changes merely to demonstrate benefit.

No device, bundle or maintenance reduction measurements were made here. DB's alpha status and Pacer's beta status require explicit owner acceptance plus compatibility/code-reduction proof and rollback; publication under `latest` does not waive that gate. The strongest next investigation is simplifying the existing Query adapters. No evidence here warrants replacing financial storage, adopting automatic replay or reopening web SWR and the controller-owned snapshot.

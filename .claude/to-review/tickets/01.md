## What to build

The server and assistant groundwork for To review. Nothing visible changes in the clients yet, but every later ticket depends on it.

- **Per-member limit.** A member can have at most 100 active Drafts in a Group, counted for that member alone. Today it's 100 across the whole Group. Another member's Drafts never block you. At the limit, creating Drafts fails cleanly with a message the member can act on.
- **Who prepared a Draft, and who last changed it.**
  - Every Draft records who prepared it: the member themself, or a Connected assistant with its display name (for example "Claude", "ChatGPT").
  - Every change records who made it.
  - Both come from the authenticated session or connection, never from request or tool arguments.
  - Existing Drafts without this read as prepared by the member.
- **The assistant speaks "To review".**
  - The Draft tools' descriptions use To review language and state the per-member limit.
  - A successful creation result gives the assistant a member-facing line ("Added 3 to To review in Splitbook") and a link to that Group's To review page, `/groups/<id>/review` on the web. The web To review page and Android's handling of the link come in later tickets of this spec; until then it may not resolve, which is fine behind the flag.
- **Glossary.** `CONTEXT.md` gains **To review** and **Finish later**. The entries are already drafted on the local branch `docs/to-review`; the orchestrator will paste them into this PR if you can't reach that branch.

## Acceptance criteria

- [ ] The active-Draft limit is 100 per member per Group. Other members' active Drafts don't count, and discarded or saved ones don't count.
- [ ] A creation that would take the member past 100 creates nothing. It returns a stable error code and the member-facing text "You have 100 items waiting in this Group. Save or delete some before keeping more." The batch maximum of 10 per request is unchanged.
- [ ] Concurrent creations can't push one member past 100: with 95 active, two concurrent requests of 5 leave exactly 100. They are still serialized under the Group transaction fence.
- [ ] Each Draft read returns who prepared it (`member`, or `assistant` with a display name) and who last changed it, in the same shape.
- [ ] The assistant display name comes from the authenticated connection. A test proves a forged name in tool arguments is ignored.
- [ ] Draft records created before this change read as prepared by the member, with no migration needed.
- [ ] MCP Draft tool descriptions say "To review" and "100 per member per Group". No tool can save a Draft as an Expense.
- [ ] Creation results include the member-facing summary line and the Group's To review link.
- [ ] Ledger-only connections still can't list or read Drafts. Revoked connections are still refused immediately.
- [ ] `CONTEXT.md` has the To review and Finish later entries.
- [ ] Integration tests at the HTTP route and MCP tool boundary, against an isolated transaction-capable MongoDB, cover every point above. Prior art: the expense Draft service integration tests and the MCP connection test suite.
